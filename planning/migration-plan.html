Horde - Strangler Migration Plan

From wezfleet (PowerShell) and wezurrect (Lua) to one session-state engine with pluggable layout hosts. Written 2026-09-29 against measured state of both repositories. Supersedes the order of work in YedPool/wezfleet's planning/wezfleet-v3-rewrite-proposal.html: same destination, different route. This is the plan's only copy; the one in wezfleet points here.
The whole plan in four sentences. Replace the system module by module while it keeps running, reading before writing and deleting last. Put a versioned JSON contract between the session-state engine and anything that draws terminals, so WezTerm is one host and VS Code is another. Treat session state as the truth and layout as a suggestion, so a restore never depends on a picture of the screen. And give the Horde's roles a place in the schema, so "exactly one Warchief" is something the system checks rather than something everyone remembers.

1. The decisions this plan rests on

D1. A new repository, Horde, built as a strangler of the other two

Decided 2026-09-29. Horde is its own private repository. The old wezfleet and wezterm-resurrect repositories stay intact and keep running the fleet throughout.

An earlier draft of this plan argued the opposite - migrate inside wezfleet - on the grounds that a third repository adds a synchronisation problem while two already exist. That cost is real, and this is how it is paid: Horde never writes to the old systems' state until a step's switch. Its first module only reads their stores. So there is no two-way synchronisation to keep correct; there is one-way reading, which cannot corrupt anything, and a sequence of deliberate, shadowed handovers. What the new repository buys in return is a clean start - structure, history and naming - without carrying the shape of the search that produced the old ones.

File references in this plan are to YedPool/wezfleet unless another repository is named.

D2. Read first, write second, delete last

A new reader cannot break anything, because it changes nothing. So the first real module is a projection that reads every existing store and writes none. Consumers move onto it one at a time. Only when every reader goes through it do writers move, because only then can storage change without any consumer noticing. Deletion comes after the replacement has run in production.

D3. Session state is authoritative; layout is advisory

A restore must bring back every session with the right identity, directory and conversation even if no layout was saved at all. Layout only arranges them. This one rule removes the pane-hijack class structurally: a layout slot refers to a session by its stable id, and the pane it lands in is recorded afterwards as derived fact, never as identity.

D4. Contract before code

Three versioned JSON schemas with golden fixture files that both languages validate against: the session record, the restore plan, and the existing pane-sessions record. Today the Lua reads a format the PowerShell writes and nothing states what it is, so neither side's tests can see the other. That gap is where the hijack lived.

D5. Degradation lives in the engine, not in the adapters

Each host declares what it can do. The engine is told those capabilities and hands the host a plan it can apply completely. Adapters stay dumb and each degradation rule is written and tested once, instead of every host inventing its own idea of what to do when it cannot split a pane. (Capability negotiation; the same idea as the agent capability matrix.)

D6. Shadow before switch

Every time the new path takes over from the old one, it first runs beside it: both compute a result, the differences are logged, the old result is still the one used. Only after a run of clean comparisons does the default flip, and the old path stays behind a flag for one more phase. (Parallel run, also called dark launch.)

D7. Ratchets, not promises

Every "we will convert the rest later" becomes an allowlist that a test forbids from growing. The allowlist can only shrink. This is the mechanism that stops a strangler stalling halfway and leaving two systems forever, which is the characteristic way these migrations fail.

The repository already has one, and the plan extends it rather than inventing a second. test_debug/test-ssot.ps1 names every file still reading the roster and fails on a new one or on a declared one that has since been cleaned up - so the list cannot silently go stale in either direction. Horde's ratchets - the adoption ledger in phase 3 and the ownership table in phase 0 - are built the same way, and live in Horde.

D8. The engine stays PowerShell during the migration

Changing language mid-migration doubles the moving parts. The contract is JSON on purpose, so the engine's language can be revisited after the migration without touching any host.

D9. No module is replaced until its knowledge ledger is complete

The instruction: every piece rebuilt with the correct structure and the utmost attention to detail, which means actually reading the old code, pull requests and documentation that hold hard-earned knowledge. Measured, that knowledge is large and scattered: 

  wezfleet   124 commits, 108 with explanatory bodies (3,832 message lines)
             12 PRs, 15 planning docs (3,170 lines), 4 BUG write-ups
             tasks/lessons.md: 24 entries
             3,551 comment lines in lib/ - 35% of the library is explanation
             70 dated measurements in comments
  wezurrect  451 commits, 69 PRs, 8 planning docs, 778 comment lines

Too much to read once and remember, so it is harvested just in time, per module. Before a step replaces a module, planning/ledger/<module>.md is written from five sources: the module's own comments; git log --follow of every file it spans; every pull request that touched those files, in both repositories; every planning, BUG and lessons entry that names it; and its tests, where each test name is a behaviour someone once needed.

Every entry carries a citation - commit, PR, document or file:line - and exactly one disposition: encoded as a test in the replacement, carried as a comment, or deliberately dropped, with the reason. A gate test fails on any entry without one, and the replacing pull request links its ledger. Nothing is lost silently, because "we did not look" becomes a visible empty field instead of an absence.

Why this is not optional, from this plan's own history: its first version asserted the Warchief had no field and no invariant, without reading Hierarchy.ps1 or Master.ps1. Both existed. A ledger for the hierarchy module would have made that impossible.

D10. Branches, worktrees, atomic commits, tightly scoped pull requests

Every step is done on its own branch in its own worktree, in the one folder beside the repository, created from a freshly updated main. From the repository root: 

  git fetch origin main
  git worktree add -b <branch> ../horde-worktrees/<name> origin/main

One logical change per commit, independently revertible. One concern per pull request, merged as a regular merge commit, never squashed. Worktrees are what make this safe here rather than merely tidy: the house rule is never to switch branches under a running suite, and a worktree is a separate checkout, so work continues while tests run. They are also known to work - repo identity comes from git rev-parse --git-common-dir, so a worktree files runs under the same store, and every commit of this migration's first pull requests was verified from its own worktree.

D11. Battle-tested: the fleet runs on each piece before it counts

Instruction, 2026-09-29: as much real end-to-end, user-simulated testing as possible, and the fleet moved onto the new system piece by piece so that it is actually battle-tested.

So every step that takes something over has a third gate, after its tests and its ledger: the live fleet uses it for real work. Concretely, in the order the phases produce them -

  • Phase 2 - the Warchief's own status checks run horde status beside the old wezfleet status, and every disagreement is logged. The read model is proved by the session that depends on it most.
  • Phase 3 - each command that moves onto the projection is used by the Orcs for their real work before its entry leaves the ratchet.
  • Phase 4 - restores shadow on real WezTerm starts, not only in a test instance, and the default flips only after a run of clean comparisons on the real layout.
  • Phase 7 - a real Goblin is spawned into a VS Code terminal and does real work.

Alongside that, an end-to-end suite drives the real horde command line the way a person or an orchestrating session would - spawn, report, message, restore, read status - inside an isolated WezTerm, asserting on what a user would see and on the state left behind. It is built in Phase 0, before there is much to drive, so every later step lands with a scenario rather than acquiring one afterwards.

The reason this is a gate and not a preference: the systems being replaced were repeatedly green in their suites and wrong in use. A mechanism once existed, worked and had no callers while three suites agreed it was fine. Use by the real fleet is the one test that cannot be passed by testing the wrong thing.

D12. The set of hosts is open: WezTerm and VS Code are the first two, not the only two

Instruction, 2026-09-29: keep in mind that Horde may expand beyond WezTerm - tmux, Ghostty, psmux, VS Code and others.

The ports in section 2 already make a host an adapter. This decision makes three consequences of that explicit, so the first host cannot quietly become an assumption:

  • Nothing outside hosts/<name>/ names a terminal. The engine, the schemas and the read model speak of sessions, slots and capabilities. A WezTerm pane id is a host handle, stored in a realisation, never a key.
  • Host-specific test tooling lives with its host. The isolated-instance harness is WezTerm tooling; it moves under a WezTerm path once its pull request lands, and the next host brings its own isolation (for tmux, a private server socket with -L).
  • A new host is a new column in the capability table, not a change to the engine. Candidates, each to be measured before it is claimed: tmux (splits, capture, runtime text through its own CLI), psmux (tmux's model on Windows), Ghostty (a terminal whose scripting surface must be verified before anything is promised for it).

The test of the decision is Phase 7: if adding the second host needs an engine change, the seam was drawn in the wrong place, and that is fixed before a third host is attempted.

2. The Horde, as architecture

Correction to the first version of this section

It said the master orchestrator was a convention, "with no field anywhere that says so and nothing that would notice two of them." That was false, and it was written without reading the two files named after the thing it described. role is already a field on every session record (lib/Registry.ps1:431). lib/Hierarchy.ps1 already holds "master orchestrator (exactly one)" as an invariant and reports two masters as a finding rather than choosing between them. lib/Master.ps1 already has Invoke-WfMasterEnsure, an idempotent command designed 2026-09-11 with a careful argument for who may start a master and who may not. This is the reason for decision D9: a claim about what the system lacks is checked against the system before it is written down.

So the naming scheme does not create structure. It renames structure that exists and works - which is a smaller change and a more dangerous one, for reasons the repository has already paid for.

Why renaming a stored value is the risky part, from this repository's own history

The obvious way to rename master to warchief is to rewrite every record. That would push every record through the one write path that has lost role twice:

  • 2026-09-11: a writer rebuilt records from a fixed key list, and role and parent were gone within one write. The fix, "merge, never replace - including fields this function has never heard of", is at lib/Registry.ps1:292.
  • 2026-09-15: A's record lost its role, label, owner and parent in a four-minute window with two tool calls in one second. A harness of three concurrent writers deleted the file in 22 of 25 rounds, because every writer used the same temp name and a replace over an existing file is not atomic (lib/Registry.ps1:130).

A separate repository removes that risk entirely rather than managing it (step 0.8). Horde speaks the new vocabulary natively and maps wezfleet's old values through one alias table as it reads them. wezfleet's records are never rewritten, its nine literal comparisons are never touched, and its writer is never exercised by the rename at all. Old values stay readable for as long as any record could hold one, because records outlive the sessions that wrote them. A test proves Horde opens no wezfleet file for writing.

What this changes in the design

The cardinality checks move into the projection, so every consumer sees them instead of only the commands that call Get-WfHierarchyFindings - reported with the same three-valued honesty as everything else: if the registry cannot be read, the Warchief count is unknown, not zero.

And the point about the orchestrator being a client of the system still stands: Thrall's decisions - what work exists and who holds it - belong in the Horde's records, so any session can take the Warchief role cold after a compaction. That is the one genuinely missing piece, and it is smaller than the first version of this section implied.

How the vocabulary migrates

  • No rename of the old system at all. wezfleet keeps its words for as long as it runs. Horde speaks the new vocabulary from its first line, and one glossary maps old to new for anyone reading both during the overlap.
  • horde is Horde's own command, separate from wezfleet, which keeps working unchanged until the fleet has moved off it. Thrall is a role, not a command: it names whichever session currently holds role: warchief, so it appears in records, logs and prose, never as a binary.
  • Existing letter labels (A, B, D...) survive as labels. Role and label are different facts: role is what a session is, label is what humans call it.
  • horde.yaml carries a real cost here. Windows PowerShell 5.1 has no built-in YAML parser, so YAML manifests mean taking a module dependency. Recommendation: horde.json now, same name, and revisit the format with the engine language (D8).

Why two ports on a host instead of one. TerminalPort operates on live panes - it already exists as lib/Hosts.ps1, eight verbs with a conformance suite. LayoutPort is about arrangement: taking a snapshot and reproducing one. They answer different questions and fail differently, and a host can support one without the other - VS Code can apply a layout but cannot read a terminal's text from outside the editor. Keeping them separate means the capability matrix can say that precisely instead of pretending a host is all-or-nothing.

4. The layout abstraction

Why WezTerm's own format cannot be the contract

wezurrect saves WezTerm's pane tree: workspaces, windows, tabs, and splits with sizes in WezTerm's own terms. VS Code has no splits in that sense - it has terminal groups. tmux has windows and panes but no workspaces. A plain console has processes and nothing else. If the saved format is one host's native shape, every other host has to reverse-engineer it. So the plan describes arrangement logically, and each host maps the logic onto what it has.

The restore plan, v1

{
  "schemaVersion": 1,
  "planId": "20260929-214500-horde",
  "sessions": [
    { "slot": "s1", "sessionId": "aaaaaaaa-...", "agent": "claude", "role": "orc",
      "label": "D", "cwd": "C:\\Users\\...\\wezfleet",
      "resume": { "kind": "claude-resume", "id": "aaaaaaaa-...",
                  "argv": [ "claude", "--resume", "aaaaaaaa-..." ] } },
    { "slot": "s2", "sessionId": "bbbbbbbb-...", "agent": "codex", "role": "goblin",
      "label": "D1", "parent": "aaaaaaaa-...", "cwd": "C:\\...",
      "resume": { "kind": "codex-resume", "id": "bbbbbbbb-...",
                  "argv": [ "codex", "UNMEASURED-placeholder-see-plan-step-5.1", "bbbbbbbb-..." ] } }
  ],
  "layout": {
    "advisory": true,
    "workspaces": [ { "name": "wezfleet", "windows": [ { "tabs": [
      { "title": "D wezfleet orc",
        "root": { "split": "right", "ratio": 0.6,
                  "children": [ { "slot": "s1" }, { "slot": "s2" } ] } }
    ] } ] } ]
  }
}

Every leaf of the layout is a slot, and every slot names a session by its stable id. Nothing in the plan is keyed by a pane number. The resume block is produced by the AgentPort, and its argv is the exact command a host runs, program first and one argument per element. A host never turns kind into flags itself, so the Lua no longer needs to know that Claude resumes with --resume or how Codex does it - it runs the command it is given. kind says which AgentPort built it: claude-resume, whose id is the session's own id and whose argv is claude --resume <id> (read off 12 live Claude processes on 2026-09-30), or codex-resume, whose command is not yet measured (step 5.1): its argv above is a placeholder and says so. No two sessions share a kind and id, so no conversation is resumed twice.

Which harness, provider and model each session runs on - engine settings, the agents/<name>/ adapters, provider profiles, the session key and resume bindings: planning/execution-plan-engines.md (2026-09-30).

Degradation rules, applied by the engine

  1. Sessions are never dropped. Every slot in the plan appears in the host's output, whatever happens to the arrangement. This is D3 made mechanical.
  2. Splits deeper than the host supports are flattened into sibling containers at the deepest supported level, preserving left-to-right, top-to-bottom order.
  3. No tabs: each tab becomes its own window if windows are supported, otherwise its own terminal. VS Code / Cursor has one window and no tabs of its own, so a plan for it is one window (one folder), and each tab becomes a terminal group in that window, keeping its title.
  4. No workspaces: workspace names become a prefix on window or terminal titles, so the grouping is still visible to a human.
  5. No sizes: ratios are dropped. Never approximated, because a guessed size looks like a bug.
  6. The result is recorded as a realisation: which slot landed in which host handle. That is derived, current, and rebuilt on every restore - never used as identity.

7. What stays Lua, permanently

Measured against the 4,930 lines of plugin Lua. These have no equivalent outside WezTerm's own process, so they remain as the WezTerm adapter - estimated at 150 to 250 lines once the logic has moved.

  • gui-startup - the only way to act before the first window paints.
  • InputSelector and PromptInputLine - the interactive picker.
  • update-status and format-tab-title - status bar and tab decoration, including the Horde's imagery.
  • Key bindings through action_callback.
  • In-process events: user-var-changed, pane-focus-changed.

Everything else - instance bookkeeping, persistence, relaunch decisions, tree capture - is logic that happens to be written in Lua, and moves.

Added risk from moving to a separate repository

Horde reads files that wezfleet is writing at the same moment. wezfleet's record writer has already been measured losing and even deleting a record under concurrent writes (lib/Registry.ps1:130, 2026-09-15), and was fixed with unique temporary names and atomic replacement. A reader can still arrive in the gap: a file absent for a moment, or unparseable. Horde reads such a file as unknown, never as absent - so a record caught mid-write produces a "cannot tell" for one read, not a session declared gone. That is exactly the case core/tristate exists for, and it has an end-to-end scenario: read continuously while a writer loops.
